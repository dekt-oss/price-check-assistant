## 1. 프로젝트 한 줄 요약과 배경

병원 관리부 구매 담당자가 **견적서를 올리거나 모델명을 입력하면**, 조달청 나라장터(G2B) 납품실적·계약정보,
제조사 공개가격, 식약처(MFDS) 의료기기 정보 등을 모아 **"이 견적가가 시장가격 대비 어떤지 검토할 근거"**를
보여 주는 공개 PoC입니다. 근거가 부족하면 가격을 만들어 내거나 높다/낮다를 자동 판정하지 않는 것이 원칙입니다.
최근에는 병원 News Radar, 병원 경영 Benchmark 같은 확장 모듈이 붙었습니다.

- 운영 주소: https://bp-price-research.streamlit.app (Streamlit Community Cloud, Python 3.14)
- 주요 사용자: 개발자가 아닌 병원 구매 담당자 1~수 명. 데스크톱 브라우저 사용.
- 개발 방식: 사람 1명 + AI 에이전트 여러 개(Claude Code, Codex)가 PR 단위로 작업. 지금까지 PR 370개 이상.

## 3. 리뷰 범위 — 다섯 영역

각 영역마다 아래 질문에 답해 주세요. 질문 목록은 출발점일 뿐이니, 더 중요한 문제를 찾으면 그쪽을 우선합니다.

### A. 페이지 구성과 UI/UX

1. **정보 구조**: 화면 16개 중 실제 사용자(구매 담당자)에게 필요한 것은 몇 개인가? UAT·진단·Phase0 같은
   개발자용 화면이 사용자 메뉴에 섞여 있지 않은가? 메뉴 이름과 순서가 업무 흐름(견적 받음 → 비교 근거 확인 →
   결재 자료 작성)을 따르는가?
2. **핵심 과업 완료 시간**: "견적서 1장을 올리고 결재에 쓸 수 있는 근거를 얻기까지" 몇 번 클릭하고 몇 초
   기다리는가? 운영 주소에서 직접 해 보고 단계별로 기록해 주세요.
3. **결과 화면의 이해도**: 근거가 없을 때, 조건이 다를 때(`OBSERVED_ONLY`), 부분결과일 때 사용자가
   그 의미를 오해하지 않는가? 경고·주석 문구가 너무 많아 정작 중요한 것이 묻히지 않는가?
4. **일관성**: 표 정렬·필터·링크·빈 상태·로딩 표시가 화면마다 같은 방식인가?
5. **Streamlit 한계**: 지금 겪는 UX 문제 중 Streamlit 구조(매 상호작용마다 전체 스크립트 재실행, 세션 상태)
   때문에 생기는 것은 무엇이고, Streamlit 안에서 해결 가능한 것과 불가능한 것을 나눠 주세요.

2. **스키마**: `models.py`와 `alembic/versions/`를 보고 정규화 수준, 키 설계(중복 제거용 SHA-256 키 포함),

## 5. 결과물 형식

파일: `docs/coordination/history/FULL_REVIEW_2026-10_codex.md`. 맨 위에 리뷰한 커밋 SHA와 리뷰 날짜를 적고,
아래 순서로 씁니다.

1. **총평** (10줄 이내): 지금 가장 큰 문제 세 가지와, 이대로 계속 가면 3개월 뒤 무엇이 터질지.
2. **측정 결과표** (D-1, D-2): 항목 / 측정값 / 측정 방법 / 측정 일시.
3. **발견 사항 목록**: 각 항목을 아래 형식으로. 심각도 높은 순서로 정렬합니다.

   ```
   ### [영역-번호] 한 줄 제목
   - 심각도: 치명 / 높음 / 중간 / 낮음
   - 영역: A(UI/UX) / B(DB) / C(운영) / D(속도) / E(코드)
   - 증상: 사용자나 운영자가 실제로 겪는 일 (쉬운 말로)
   - 근거: 파일:줄, 화면 캡처 설명, 측정값, 재현 순서 중 하나 이상
   - 원인: 한 문장
   - 제안: 무엇을 어떻게 바꿀지. 대안이 있으면 장단점 한 줄씩
   - 예상 효과와 비용: 효과(가능하면 숫자), 작업량(S: 반나절 / M: 2~3일 / L: 1주 이상), 위험
   - 확인 여부: 확인함 / (추정)
   ```

4. **개선 로드맵**: 발견 사항을 묶어서
   - 이번 주에 할 것(작고 효과 큰 것, 특히 속도),
   - 이번 달에 할 것,
   - 구조를 바꿔야 하는 것(예: Streamlit 유지 여부, 저장소 정본 재정리) — 이건 결정에 필요한 정보와
     선택지만 쓰고 결론은 제가 내립니다.
5. **하지 말아야 할 것**: 지금 하고 싶어 보이지만 효과에 비해 비용이 큰 작업.
6. **과거 리뷰 지적 사항 추적표**: 과거 `REVIEW_*.md`의 주요 지적이 지금 고쳐졌는지 / 일부 / 안 됨.
7. **확인하지 못한 것**: 시간·권한·키 부족으로 못 본 범위와, 그 때문에 결론이 바뀔 수 있는 부분.

## 6. 좋은 리뷰의 기준

- 발견 사항마다 **근거가 있다**: 파일 위치, 측정값, 재현 순서 중 최소 하나.
- 제안이 **실행 가능하다**: "리팩터링 필요" 대신 "X 함수를 Y 파일로 옮기고 Z 캐시를 씌운다".
- 우선순위가 **사용자 체감 기준**이다: 코드가 예쁘지 않은 것보다 사용자가 기다리거나 오해하는 것이 먼저.
- 비개발자가 읽어도 각 항목의 "증상"과 "제안"만 보고 무엇이 문제인지 이해할 수 있다.
