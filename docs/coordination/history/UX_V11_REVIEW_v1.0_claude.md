## 1. 총평

방향은 맞지만 출발점이 틀렸다. 7개 목표 중 "검색 결과 상단 결론", "기간 선택", "제품군 시세", "연도별 표", "3건 미만 판단 보류", "20% 초과 확인 필요"는
2026-10-07~10-11 사이에 이미 운영에 들어갔다(PR #284~#332). 작업지시서가 이것을 "새로 만든다"고 쓰면 두 번째 작업자는 기존 presenter를 모른 채 중복 구현을 하고,
기존 계약 테스트(화면 금지어 검사, 배포 마커 14곳)를 깨뜨린다. 진짜 공백은 세 가지다. ① **지표 정의가 어디에도 문서로 없다**(중앙값은 코드마다 따로 계산한다:
`result_summary._median`, `category_market.median`, `device_page`의 `statistics.median`, `purchase_workspace`). ② **속도의 병목은 검색이 아니라 기동 시
인덱스 내려받기(최대 58초)와 Streamlit Cloud 메모리 한도(약 2.7 GB, 파일 캐시 포함)**인데 "캐시·사전집계"만 말하면 해결이 안 된다. ③ **"구매 판단 카드"라는
이름 자체가 이 서비스의 핵심 원칙("적정 판정을 하지 않는다", `result_summary.py` 6행, wireframes 규칙)과 충돌한다.** 이 셋을 Phase 0에서 먼저 못 박지 않으면
나머지 단계는 각자 다른 숫자를 보여주는 화면이 된다.

## 2. Critical / High 문제

### C1. "구매 판단 카드"는 서비스 원칙과 충돌한다 (Critical)
- **요구사항**: 검색 결과 상단 구매 판단 카드 (목표 1).
- **실패 상황**: 담당자가 카드의 "판단"을 결재 문서에 그대로 옮긴다. 공급사가 "시스템이 적정이라 했다/아니라 했다"를 근거로 이의를 제기한다. 거래 3건·단위 혼합·VAT 미확인 상태에서도 카드가 "판단"을 내놓으면 감사에서 산식 근거를 설명할 수 없다.
- **이유**: Track B 거래행은 `prdctUprc`만 쓰고 VAT 포함 여부가 없다(`track_b_transactions.py` 213행 `"VAT": "미확인"`). 조건동등성이 없는 자료로 "판단"은 불가능하다는 것이 README 전체의 전제다. 현재 코드도 판정 어휘를 `거래 범위 안 / 확인 필요 / 판단 부족` 세 가지로 제한한다(`quote_review_layout.py`).
- **수정 조건**: 이름을 **"거래가 비교 결과"**(또는 "확인 결과")로 바꾸고, 상태는 기존 3개를 그대로 쓴다. 카드에는 항상 ① 비교 건수 ② 기간 ③ 단위 ④ "VAT·설치 조건 미확인" 한 줄이 붙는다. "적정/비싸다/싸다/구매 권장/대체 가능"은 금지어 목록(`has_banned_term`)에 추가하고 계약 테스트로 막는다.

### C2. 동일 모델 가격과 제품군 가격이 같은 화면에서 같은 모양으로 보인다 (Critical)
- **요구사항**: 동일 모델 기간별 변동 그래프(목표 3) + 제품군 중앙·평균·상위 모델(목표 4).
- **실패 상황**: HeartOn A16-DS 중앙값 1,980,000원(같은 제품 93건) 옆에 "저출력심장충격기 제품군 중앙값 3,400,000원"이 같은 크기 카드로 보인다. 담당자가 둘을 섞어 "시세보다 42% 싸다"고 보고한다. 반대로 거래 0건 모델에서는 제품군 값만 있는데 이것을 그 모델의 가격으로 읽는다.
- **이유**: 제품군 시세는 이미 `category_market.py`가 **"참고 시세"**로만 제공하며, 동일 모델 거래가 없을 때 노출되는 보조 정보다(#326). 두 집단은 모집단·제외 규칙(동물용·부품·다른 단위·3배 이탈)이 다르다.
- **수정 조건**: 화면 계층을 고정한다. **같은 제품 거래가 1건 이상이면 제품군 값은 결론 영역에 절대 올리지 않고**, "같은 품목의 다른 모델" 섹션 안에 회색 "참고 시세"로만 둔다. 거래 0건일 때만 결론 영역에 "이 모델의 거래는 없고, 같은 품목 N개 모델이 ○○원(가운데 값)에 거래됐습니다"로 올린다. 색·카드 모양·용어("가운데 값" vs "품목 참고 시세")를 다르게 하고 AppTest로 두 경로를 고정한다.

### C3. 지표 산식이 문서화되어 있지 않고 구현마다 다르다 (Critical)
- **요구사항**: 평균·중앙·건수·순위(목표 3, 4) (원문의 산식 유무는 확인 필요).
- **실패 상황**: 결과 화면의 "93건"과 Excel의 건수, 견적 검토 페이지의 건수가 다르다(한쪽은 변경차수 포함, 한쪽은 입력오류 제외). 사용자가 "어느 숫자가 맞냐"고 묻는데 답할 수 없다.
- **이유**: 중앙값 계산기가 4곳, 이탈 규칙이 2곳(`OUTLIER_FACTOR=3` in result_summary, `PRICE_FACTOR=3`·`PRICE_RULE_MIN_ROWS=4` in category_market), 입력오류 제외는 10-10 이후 일부 경로에만 적용(마커 `*_ENTRY_ERRORS_V1`). 변경차수(`cntrctDlvrReqChgOrd`, 행의 약 11%)의 supersession 처리가 서빙 인덱스에서 어떻게 되는지 화면 문서에 없다.
- **수정 조건**: Phase 0에서 **`docs/METRIC_DEFINITIONS.md` + 단일 모듈 `services/price_metrics.py`**(순수 함수)로 통일하고, 모든 화면·Excel·리포트가 이것만 호출한다. 5장 산식이 그 초안이다.

### H1. 검색 속도 목표가 실제 병목을 겨냥하지 않는다 (High)
- **요구사항**: 검색 속도·체감 대기시간 개선, 캐시·사전집계·지연 로딩(목표 2). 목표 숫자는 원문 확인 필요.
- **실패 상황**: 앱이 재시작된 직후(배포·리소스 한도 초과 뒤 자주 일어남) 첫 사용자는 인덱스 내려받기를 기다린다(빈 캐시에서 3개 인덱스 58초, 제품 목록은 26.5초 후). 이 구간은 어떤 검색 캐시로도 줄지 않는다. 반면 따뜻한 상태의 검색은 identity 약 2초, 실시간 보강 약 0.85초 수준이라 이미 빠르다.
- **이유**: 병목은 ① 1.6 GB 식약처 identity 인덱스 + 0.66 GB Track B를 디스크로 내려받는 기동 과정, ② Streamlit Cloud가 파일 캐시까지 메모리로 세는 한도(약 2.7 GB, #311/#312), ③ 식약처 형명 API 28~59초(이미 버튼 뒤로 미룸). `st.cache_data`는 검색 경로에 하나도 없지만 그것이 느린 원인도 아니다.
- **수정 조건**: 목표를 **두 개로 분리**한다. (a) 따뜻한 상태: 결론 영역 첫 그림 ≤ 3초, 실시간 보강 포함 전체 ≤ 10초. (b) 차가운 상태: 10초 안에 진행률 표시, 검색 가능 시점 ≤ 30초. 측정은 이미 있는 숨김 마커 `purchase-search-timings-v1`의 단계별 값으로 하고, 목표를 쓰기 전에 운영에서 1주일치 분포를 먼저 수집한다. "사전집계"는 앱 안이 아니라 **GitHub Actions 동기화 작업이 R2에 모델별 요약 파일(수 MB)을 미리 써 두는 방식**이어야 한다. 앱 메모리에 쌓는 사전집계는 리소스 한도를 다시 터뜨린다.

### H2. 평균가격을 헤드라인 지표로 쓰면 묶음 거래가 수치를 끌고 간다 (High)
- **요구사항**: 제품군 평균가격(목표 4).
- **실패 상황**: M40 환자감시장치에서 "2 set 73,026,000원"(1 set당 36,513,000원, 사업명 「취약지 응급의료기관 장비지원사업」) 한 줄이 평균을 4,400,000원대에서 수백만 원 위로 올린다. 담당자가 평균을 보고 견적이 "싸다"고 판단한다.
- **이유**: 나라장터 한 줄은 장비 1대가 아니라 사업 단위 묶음일 때가 많고, 단위(대/set/식)가 섞인다. 그래서 현재 코드는 **중앙값만** 쓰고 3배 이탈을 따로 보여준다.
- **수정 조건**: 평균은 헤드라인에서 제외. 꼭 넣어야 하면 "상세 자료" 안에 **수량가중 평균(거래금액 합 ÷ 수량 합, 같은 단위만)**을 n과 함께 두고 "묶음 거래 영향 있음"을 붙인다. 산술평균은 쓰지 않는다.

### H3. "동일 모델" 기간별 그래프는 모델 문자열 분절과 희소 데이터로 거짓 추세를 만든다 (High)
- **요구사항**: 동일 모델 기간별 가격 변동 그래프(목표 3).
- **실패 상황**: 2024년 2건·2025년 1건·2026년 5건인 모델에서 선 그래프가 "가격 30% 하락"을 보인다. 실제로는 2025년 1건이 옵션 포함 거래였다. 또 `DFM100`과 `SJ-DFM100`이 다른 선으로 갈라져 각각 반쪽 추세를 그린다.
- **이유**: 식약처 identity는 exact key + 약한 키 보강(#256)이고 별칭 등록부(`data/model_aliases.csv`)는 4건이다. 연도별 건수가 3건 미만인 구간이 흔하다(PNB-704처럼 연 12~27건인 모델은 소수). 현재 연도표(`year_summary_rows`)는 숫자만 보여 과장이 없다.
- **수정 조건**: 그래프는 **연 단위 중앙값 점 + 최저~최고 수직 범위**로만 그리고, 구간 n<3이면 점을 비우고 "거래 n건"만 쓴다. 선으로 잇지 않는다. 변동률 문구는 두 구간 모두 n≥3일 때만 생성한다. 분기 단위는 연 12건 이상일 때만 허용한다.

### H4. 뉴스 "주요 이슈"는 네이버 이용약관 때문에 제목·링크·도메인·시각만으로 만들어야 한다 (High)

### H5. 경영 브리핑이 "현재"처럼 읽히지만 자료는 2024 회계연도까지다 (High)

## 3. Medium / Low 개선사항

- **M1. 기본 기간 3년 자동 확장 안내가 결론과 분리돼 있다.** 지금은 캡션 한 줄이다. 자동으로 5년·전체로 넓혔으면 결론 문장 안에 "(최근 3년 거래가 없어 5년 기준)"을 넣어야 보고서 복붙 때 빠지지 않는다.
- **M2. "거래 건수"에 수량이 묻힌다.** 8 SET 한 줄과 1대 한 줄이 모두 1건이다. 건수 옆에 "총 수량 N대"를 병기하면 묶음 거래가 바로 드러난다.
- **M3. 납품업체·기관 명칭 정규화 없음.** "부산대학교병원"/"부산대학교 병원"이 2기관으로 센다. 공백·괄호·법인 접두어 정규화 함수를 5장 산식에 포함했다.
- **M4. 자료 기준일 지연이 화면에서 약하다.** Track B 서빙 인덱스 `data_as_of`가 크론 지연으로 며칠 멈춘 사례(10-05에 고정). 결론 영역의 "자료 기준" 줄에 **기준일이 3일 넘게 오래됐으면 노랑 표시**를 붙인다.

## 5. 지표 정의 검토 (제안 산식)

공통 전처리 **P**: ① 서빙 인덱스에서 같은 `(cntrctDlvrReqNo, prdctSno)`는 최종 변경차수 1행만 남긴다. ② 단가는 명시된 `prdctUprc`만 쓴다(금액÷수량 역산 금지, 현행 유지). ③ 입력오류 의심(단가 0~10원, 단가·수량 뒤바뀜) 제외. ④ 거래일 = 납품요구일(현 "거래일" 열)로 기간 필터. ⑤ 단위를 정규화하고 **최다 단위만** 가격 계산에 쓴다(다른 단위는 별도 나열).

| 지표 | 산식 | 포함 | 제외 | 표시 조건 |
| --- | --- | --- | --- | --- |
| 동일 모델 거래 중앙가격 | P 적용 후 단가의 중앙값(짝수면 두 중앙값 평균, `statistics.median`) | identity exact 또는 검증된 별칭(`model_aliases.csv`) 일치, 선택 기간 | 약한 키 미보강 매칭, 다른 단위, 입력오류 | n≥3이면 값 표시, n=1~2는 값 나열만, 0건은 "거래 없음" |
| 제품군 거래 중앙가격 | 제품군 = 식약처 품목명과 이름이 같은 세부품명번호 + 같은 품목 모델이 실제 거래된 코드(점유 20% 이상). 장비 구매로 분류된 행의 단가 중앙값 | 모델 미기재 행 포함(점유율 병기) | 동물용, 부품·수리, 다른 단위, 중앙값 대비 3배 초과·1/3 미만(현행), 입력오류 | n≥4(현행 `PRICE_RULE_MIN_ROWS`). 항상 "참고 시세" 라벨 |
| 제품군 평균가격 | **수량가중 평균 = Σ(단가×수량) ÷ Σ수량**, 같은 단위·같은 제외 규칙 | 위와 동일 | 위와 동일 | 상세 영역만. 중앙값과 20% 넘게 차이 나면 "묶음 거래 영향" 문구 |
| 예상 조정 가능액 | **"가운데 값과의 차액"**으로 명명. = max(0, 견적 단가 − 동일 모델 중앙가) × 견적 수량 | 판정이 "확인 필요"(n≥3, 견적>중앙가+20%)일 때만 | 단위 불일치, 견적 단가 미인식, 제품군 중앙가 기준 계산 | 금액 옆에 "VAT·설치 조건 확인 전 참고값". "절감액" 표현 금지 |
| 거래 건수 | P ① 적용 후 행 수(모든 단위) | 선택 기간 | 변경 전 차수 | "거래 N건 (가격 계산 M건, 총 수량 Q대)" 형태 |
| 납품 기관 수 | 정규화한 수요기관명 distinct 수. 정규화 = 공백·괄호 제거, "(재)", "(학)" 등 법인 접두 제거, 전각→반각 | 모든 단위 | — | 명칭 변형 의심(편집거리 1)이 있으면 "N곳(명칭 변형 포함 가능)" |
| 거래 상위 모델 | 제품군 장비 구매 행에서 (허가번호, 모델) 키별 건수 내림차순. 동률은 기관 수, 그다음 최근 거래일 | 거래 2건 이상 모델 | 모델 미기재(점유율은 별도 한 줄), 동물용·부품 | 상위 5개. 순위 숫자 대신 건수 막대로 표시(순위가 품질로 읽히는 것 방지) |
| 가격 변동률 | 구간 = 회계연도. 변동률 = (최근 완결 연도 중앙가 − 직전 연도 중앙가) ÷ 직전 연도 중앙가 × 100 | 두 구간 모두 n≥3, 같은 단위 | 올해(미완결) 구간은 "진행 중" 표시만 | 문장은 "연도 가운데 값이 X% 변했습니다", "상승/하락 추세" 단어 금지 |
| 구매 판단 신뢰도 | **점수 대신 "근거 수준" 3단계**. 높음 = n≥10 ∧ 기관≥3 ∧ 최근 12개월 거래 ∧ 단일 단위 ∧ identity exact. 보통 = n 3~9 또는 최근 거래 12~36개월. 보류 = n<3 ∨ 약한 키 ∨ 단위 혼합 ∨ 식약처 미확인 | — | — | 등급 옆에 어떤 조건이 걸렸는지 글자로 표시. 숫자 점수 표시 금지 |
| 뉴스 주요 이슈 점수 | 군집 = 72시간 창 안에서 제목 토큰(매체명 접미·특수문자 제거, 2자 이상) Jaccard ≥ 0.6. 점수 = 서로 다른 매체 수 × 2 + 그룹 가중(우리병원 3, 경쟁·의료원 2, 기타 1) + 24시간 내 +1 + 제목에 키워드 있으면 +1 | 제목·링크·도메인·시각만 | 본문, AI, 21일 지난 기사 | "주요" = 매체 2곳 이상 또는 우리병원 그룹. 군집 대표 = 가장 이른 기사, 나머지는 "같은 소식 N건"으로 접기 |
| 경영 브리핑 비교군 차이 | 비율 지표: 대상 − 비교군 평균(%p). 금액 지표: (대상 − 평균) ÷ 평균 × 100. 평균 = 유효값 있는 병원의 단순 평균, n 병기. 허용폭 ±1%p / ±5%(현행) | 같은 회계연도, 유효값 3곳 이상 | 회계기간 불일치 병원(경고 후 제외), 병상수 없는 병원의 병상당 지표 | 문장 틀: "[지표]가 비교군(N곳) 평균보다 [차이] [높다/낮다]". 원인·평가 어휘 금지 |

## 6. 단계별 구현안 재설계

모든 단계 공통 규칙: `.worktrees/`에서 작업, 대시보드 수정은 호출 줄만, 새 모듈마다 런타임 마커 상수, 화면 금지어 테스트 통과, 운영 스모크 마커 갱신, PR 하나로 머지 가능. 산출물은 `docs/` 아래 문서 + 테스트 fixture + 재개 메모(`docs/HANDOFF_<phase>.md`)로 통일한다.

### Phase 0 · 지표·데이터 계약 확정 (화면 변경 없음, 2~3일)
- **목적**: 모든 숫자의 단일 출처를 만든다.
- **포함**: `docs/METRIC_DEFINITIONS.md`(5장 표를 정본으로), `services/price_metrics.py` 순수 함수(전처리 P, 중앙값, 수량가중 평균, 건수, 기관 수 정규화, 연도 중앙값·변동률, 근거 수준), 결과 화면 데이터 계약 dataclass(`ResultContract`: 모델 요약·제품군 요약·기간·단위·자료 기준·근거 수준), 골든 fixture 4종(93건/세트 혼합/1건/0건), 상태 매트릭스 문서(4장 실패·빈 상태 9가지의 문구).
- **제외**: 화면, 그래프, 뉴스, 경영.
- **변경 영역**: `services/`, `tests/`, `docs/`. 기존 중앙값 계산 4곳은 건드리지 않고 **동일 결과 검증 테스트**만 추가.
- **선행 조건**: 없음.
- **인수 조건**: fixture 4종에 대해 기존 `result_summary`·`category_market` 결과와 새 모듈 결과가 일치. 문서에 모든 지표의 포함·제외·표시 조건이 있음. 금지어 목록 확장분이 테스트에 들어감.
- **필수 테스트**: 단위 테스트(각 함수), 동등성 테스트(기존 vs 신규), 문서-코드 일치 테스트(문서의 상수 값과 코드 상수 비교).
- **산출물**: 위 문서 2개, 모듈, fixture, `HANDOFF_P0.md`(어떤 함수가 어느 화면을 대체할 예정인지 표).
- **재개 지점**: fixture가 있으면 함수부터, 함수가 있으면 동등성 테스트부터.

### Phase 1 · 거래가 비교 결과 카드 (2~3일)

- **재개 지점**: 스냅샷 테스트가 통과하는 상태별로 재개. 중단 시 기존 presenter가 그대로 동작하므로 배포 위험 없음.

## 8. 최종 권고안

**먼저 개발할 최소 범위**: Phase 0 → Phase 1 → Phase 2a. 지표 정의 문서와 단일 계산 모듈, 이름을 바꾼 비교 결과 카드, 그리고 측정 기반 지연 로딩이다. 이 셋만으로 "첫 화면에서 결론을 읽는다"와 "숫자가 어디서 왔는지 설명할 수 있다"가 성립한다. 약 7~9일.

**보류해야 할 기능**: 산술 평균 헤드라인, 숫자 신뢰도 점수, 절감액 표현, 뉴스 AI 요약, 경영 원인 설명, 모바일 전용 레이아웃, 분기 그래프.

**가장 위험한 가정 3개**
1. "검색이 느리다"의 원인이 검색 로직이라는 가정. 실측은 기동 시 인덱스 내려받기와 플랫폼 메모리 한도가 병목임을 가리킨다. 캐시 추가는 한도를 다시 터뜨릴 수 있다.
2. 나라장터 한 줄 = 장비 1대라는 가정. 묶음·세트·사업 단위 거래가 평균과 추세를 지배한다.
3. 식약처 모델 identity가 "동일 모델"을 안정적으로 묶어 준다는 가정. exact key 기반이고 별칭 등록부가 4건이어서 그래프가 분절될 수 있다.

**먼저 검증해야 할 사용자 가설 3개**
1. 구매담당자는 "거래 범위 안 / 확인 필요 / 판단 보류" 3단계와 근거 수준 표기만으로 결재 문서를 쓸 수 있다(적정 판정이 없어도 쓸모가 있는가). 검증: Phase 1 캡처로 담당자 3명 인터뷰.
2. 제품군 참고 시세는 거래 0건 모델에서만 쓰이고, 거래가 있는 모델에서는 혼란만 준다. 검증: Phase 6 과제에서 두 값을 구분해 읽는지 관찰.
3. 경영기획자는 원인 없는 차이 문장 5개를 유용하게 본다(원인을 요구하면 설계를 바꿔야 함). 검증: 브리핑 예시 8개를 보여주고 "다음에 무엇을 보겠는가"를 묻기.

**첫 배포의 명확한 완료 기준**
- `docs/METRIC_DEFINITIONS.md`가 있고, 화면·Excel·견적 검토 페이지의 건수·중앙값이 fixture 4종에서 일치한다(테스트로 증명).
- 결과 첫 화면에 "적정·권장·절감·대체 가능·평균가격"이 없고(금지어 테스트), 카드 이름이 "거래가 비교 결과"이며 상태는 3개뿐이다.
- 모든 가격 숫자 옆에 건수·기간·단위·자료 기준일이 있다(AppTest).
- 거래 1건 이상 모델의 결론 영역에 제품군 수치가 없다(AppTest).
- 운영 타이밍 마커 7일 분포가 문서화되어 있고, 따뜻한 상태 결론 첫 그림 중위수 ≤ 3초, 차가운 상태에서 10초 내 진행률이 보인다.
- 운영 스모크(마커 vN+1)와 기존 계약 테스트 전부 통과, 배포 후 메모리 진단 피크 증가 없음.
