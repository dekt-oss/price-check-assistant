# Render-Required Verification Audit

## 언제 쓰나
- 다크모드·라이트모드처럼 **조건부로만 나타나는** 스타일 값을 바꿀 때
- 여러 화면이 쓰는 **공유 컴포넌트**를 고칠 때
- 로그인·기능플래그·운영자 권한 때문에 **평소 못 보는 화면**을 건드릴 때
- 여러 단계를 거쳐 산출물이 나오는 파이프라인(지시서 → 이미지 → 조립 영상)을 바꿀 때
- "코드는 맞는데 실제로는 이상하다"거나 "fixture 검사는 통과했다"로 검증을 끝내려 할 때

## 왜 필요한가
2개 레포가 **같은 날 독립적으로** 같은 결론에 도달했다 — *"정적 검토는 충분치 않다, 실제 실행
결과를 봐야 한다."*

- **k-vivino** `2190dd7` — `CAPTURE_SCHEME=dark`로 실제 렌더를 돌려서야 상세 화면 히어로 사진
  프레임에 카드색 74px 띠가 있는 걸 발견했다. **라이트 모드에선 흰 배경 위 흰 띠라 코드·화면
  어느 쪽을 봐도 안 보였다.**
- **k-vivino** `a049c97` — `StyleSheet.create` 안이라 `theme`을 못 읽던 고정 색상 32곳. 커밋이 직접
  적었다 — *"이 문제는 다크로 그 화면을 실제로 봐야만 보인다 — 타입 검사도 렌더 테스트도 잡아 주지
  않고, 라이트에서는 완벽히 정상이다."*
- **k-vivino** `cf7511d`→`4bff482` — 08-30에 "그려 보니 있었던" 문제를 셋 겪고 개발 전용 렌더
  스위치(`EXPO_PUBLIC_SCREEN_PREVIEW`, `__DEV__`+env 이중 잠금)를 만들었는데, **만들자마자 첫
  실행에서** 운영자 홈의 헤더 중복("머리가 둘")을 바로 잡아냈다 — 운영자 계정이 없어 애초에 볼 수
  없던 화면이었다. 이어 `54639e1`·`e3344ca`도 처음 눈으로 본 화면에서만 드러나는 결함을 찾았다.
- **k-vivino** `066b7bb` — 어제 자신이 넣은 수정("빈 칸이 넷이면 격자를 안 그린다")이 같은 컴포넌트를
  쓰는 다른 화면에선 "누를 자리"를 없애는 회귀였다. *"그려 보지 않았으면 못 잡았을 회귀다."*
- **VIDEO-ARTICLE** 2026-08-30 — 그날 잡은 배선 결함 9건 중 **최소 3건이 지시서 JSON만 보고는
  안 잡혔고 실제 조립을 돌려서야 드러났다.** 핸드오프 문서가 스스로 결론 냈다 —
  *"지시서 JSON 생성만으론 못 잡는 결함이 있어 조립까지 실제로 돌려봐야 한다."*
- **k-vivino** `73cef56` — 두 화면이 "fixture 검사만 통과했을 뿐 실제 렌더로 한 번도 확인 안 됨"을 별도로 기록했다.

## 절차

### 1. 이 변경이 "렌더해야 보이는" 종류인지 판정
다음 중 하나라도 해당하면 정적 검토로 끝내지 않는다:
- [ ] 값이 **모드·조건에 따라만** 달라지는가 (다크/라이트, 권한, 기능플래그, 빈 상태)
- [ ] **공유 컴포넌트**를 고쳤는가 (다른 화면이 그 컴포넌트를 다른 의미로 쓸 수 있다)
- [ ] 산출물이 **여러 단계 조립**을 거치는가 (중간 JSON이 맞아도 최종물이 틀릴 수 있다)
- [ ] 평소 **볼 수 없는 화면**인가 (운영자 전용, 특정 데이터가 있어야만 뜨는 블록)

### 2. 실제로 돌려서 본다
- [ ] 해당 모드로 최소 1회 렌더했는가? (`CAPTURE_SCHEME=dark`, 실렌더 스크립트, 조립 완주)
- [ ] 공유 컴포넌트를 고쳤다면 **그것을 쓰는 화면 전부**를 렌더했는가? (한 곳만 보면 회귀를 만든다)
- [ ] 볼 수 없는 화면이면 **볼 수 있게 만드는 장치**를 먼저 만들었는가?
      (k-vivino `EXPO_PUBLIC_SCREEN_PREVIEW`가 선례 — `__DEV__`+env 이중 잠금으로 운영 번들엔
      물리적으로 없게 한다. 게이트만 열고 데이터·로직은 건드리지 않는다)
- [ ] 색·대비처럼 눈으로 애매한 것은 **DOM에서 실제 값을 측정**했는가? (렌더된 색 대비 5.21 등)

### 3. 렌더로 찾은 결함을 정적 테스트로 고정한다 (중요)
렌더 검증은 매번 하기 어렵다 — 한 번 찾은 결함은 다음부터 렌더 없이 잡히게 만든다.
- [ ] 소스 문자열 검색 테스트로 옮길 수 있는가?
      (k-vivino `cap-header-no-double-head.test.ts` — 캡을 import하는 화면마다 네비 헤더가 꺼져
      있는지 검사, `brand-tint-contrast.test.ts` — 소스에서 고정 색 사용을 검색)
- [ ] 그 테스트를 **일부러 되돌려 실제로 잡히는지** 확인했는가?
- [ ] → 수단 선택은 `enforce-by-type-or-test` 판단표를 쓴다.

### 4. 범위 밖 발견은 분리한다
- [ ] 렌더하다 발견한 **이번 작업과 무관한 결함**은 그 자리에서 고치지 말고 따로 적어 둔다.
      (k-vivino `a049c97`이 별건 대비 미달을 "다크 정합성 작업이 조용히 결정할 일이 아니다"라며
      분리한 판단 — Aria의 "한 변수 한 PR" 원칙과 같다)

## 사용 방법
§1로 렌더가 필요한 변경인지 먼저 판정한다. 필요하면 §2를 병합 전에 최소 1회 돌리고, 찾은 결함은
반드시 §3으로 고정해 다음부터는 렌더 없이 잡히게 한다. "typecheck·lint·test 통과"는 이 종류의
결함에 대해 아무것도 보증하지 않는다.
