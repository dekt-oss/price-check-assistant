# Magic Number Audit

## 언제 쓰나
- 커밋/PR 직전, diff에 숫자 리터럴(임계값·범위·`.limit(N)` 등)이 새로 들어갔을 때
- "정상 범위는 대략 X~Y" 같은 가정을 코드에 박아 넣으려 할 때
- 페이지네이션·조회 개수 상한을 정할 때

## 왜 필요한가
실측 없이 prior로 박은 숫자가 나중에 실제 데이터/상황이 그 숫자를 넘어서면서 조용히 깨진
사례가 반복 관찰됐다:
- ARIA: VKOSPI "정상 15~25" 가정이 위기 상황의 역대 최고치(~96)를 거짓 결손으로 처리할 뻔함
- k-vivino: `listApprovedVenues().limit(100)`이 실제 승인 업장 164건을 못 담아 검색·상세에서
  나머지가 조용히 누락 (`5a18dfe`)
- k-vivino: 반대로 PR #27에서는 A2 아키텍처 결정을 가정이 아니라 `eval-matching.ts` 확장
  측정(28/28 baseline)으로 판단해 좋은 선례를 남김

패턴: **숫자가 "대략 이 정도면 충분하겠지"라는 감으로 정해지면, 실제 데이터가 그 감을
넘어서는 순간 조용히(에러 없이) 깨진다.** 페이지네이션 캡은 특히 위험 — 실패가 아니라
"결과가 그냥 적게 나오는" 형태라 발견이 늦다.

## 체크리스트
diff에 아래 패턴이 보이면 멈추고 확인한다:
- [ ] `.limit(N)`, `.slice(0, N)`, `LIMIT N` 등 조회 개수 상한 — N이 실제 데이터 최대 건수보다
      확실히 큰가? (근거: 실측 카운트)
- [ ] `if (x > N)` / `if (x < N)` 형태의 임계값 비교 — N이 실측 분포(과거 데이터의
      min/max/percentile)로 정해졌는가, 아니면 감으로 정했는가?
- [ ] "정상 범위는 X~Y" 식의 상수 — 위기·극단 상황의 실제 최댓값/최솟값까지 포함하는지
      확인했는가?
- [ ] 위 항목이 감으로 정한 것이라면: (a) 실측 데이터로 검증하거나, (b) 최소한 config
      상수로 분리하고 "왜 이 값인지" 근거를 주석/커밋 메시지에 남긴다. 하드코딩된 리터럴로
      로직 안에 묻어두지 않는다.

## 사용 방법
커밋 전 diff를 훑으며 위 패턴을 찾는다(`grep -n "\.limit(\|LIMIT [0-9]\|> [0-9]\|< [0-9]"` 등으로
후보를 추리고 눈으로 확인). 실측 근거가 있으면 그대로 커밋, 없으면 config 분리 + 근거 주석을
추가하거나 실측 후 진행한다.
