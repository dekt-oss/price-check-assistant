# Adjacent Path Guard Audit

## 언제 쓰나
- 가드·검증·차단 조건을 새로 추가하거나 고칠 때
- 데이터 연결(좌표계·외래키·조인 기준)을 새 방식으로 바꿀 때
- LLM 프롬프트 규칙·모델 전환·설정 기본값을 바꿀 때
- UI 표현 규칙(툴팁·라벨·색·빈 상태)을 한 화면에서 고칠 때
- 새 값·새 컬럼·새 상태(시즌 전환·모드·플래그)를 도입하거나 기존 값의 뜻을 바꿀 때 (v1.1)
- 같은 코드가 여러 실행 환경·배포 채널에서 도는 설정을 바꿀 때 (v1.1)
- "고쳤는데 어떤 화면/어떤 경로에서만 여전히 이상하다"는 증상을 진단할 때

## 왜 필요한가
이 저장소들에서 가장 자주 반복된 결함이다 — **3개 레포 20회 이상.** 형태는 항상 같다:
새 규칙을 한 경로에 넣고, 같은 일을 하는 다른 경로엔 안 넣어서 그쪽만 조용히 옛날처럼 돈다.

- **Aria** `af06fb2` — 국내 매도는 주문 직전 "이 수량 팔 수 있나"를 증권사에 재확인하는데, 해외
  매도는 `if side == "BUY":` 뿐이라 아예 안 물었다. 08-21 SMCI 매도가 거래소에서 거부되고서야
  드러났다.
- **Aria** `0fb93fd`+`725e9a0` — 가격 신선도 가드가 수급 경로엔 있고 수익률 경로(`_eval_series`)엔
  없어, 하루 결손이 "2세션 수익률"로 부풀려졌다.
- **k-vivino** `e5a620d`→`4e205b6` — 세부 제품 가격을 새 좌표계로 붙였는데 검색 결과 화면만 옛
  좌표계를 봐서, 가격 있는 제품 15,295건 중 **검색에는 59건(0.4%)만** 노출됐다.
- **k-vivino** `680462c` — "묶음 가격을 한 병 값으로 쓰지 않는다" 가드를 수집 스크립트에 걸었는데,
  대표가를 계산하는 SQL 함수 네 개는 `package_kind`·`unit_count`를 한 번도 보지 않아 24캔 박스
  값이 한 캔 값으로 노출된 제품이 279개였다.
- **k-vivino** `b2a207e` — 대칭인 두 함수 중 한쪽(`review_product_for_legacy`)에만 폴백이 빠져
  사케 50종의 체크인 버튼이 비활성이었다.
- **VIDEO-ARTICLE** `87c7dcf`·`d431340` — 원문 주입 코드는 고쳤지만 실제로 도는 워크플로엔 연결
  설정이 없어 조용히 fixture 모드로 폴백했고, 대시보드 버튼이 부르는 Edge Function엔 그 연결이

  Phase 3 배선이 스틸 분기에만 타고 영상 분기는 빠짐, `precision_layer`가 선언만 되고 렌더러 없음 등).

## 체크리스트

### 1. 인접 경로 목록을 먼저 만든다 (고치기 전에)
이 변경이 건드리는 것과 **같은 데이터·같은 판단**을 쓰는 곳을 전부 적는다. 흔한 축:

- [ ] **실행 주체가 둘인가** — 로컬 워커 vs Edge Function/서버리스 vs GitHub Actions
      (같은 로직이 두 런타임에 복제돼 있으면 둘 다 고쳐야 한다)
- [ ] **방향이 둘인가** — 조회 vs 쓰기, 정방향 함수 vs 역방향 함수, A→B 매핑 vs B→A 매핑
- [ ] **시점이 둘인가** — 수집·적재 시점 vs 표시·계산 시점 (수집에 건 가드가 표시 함수엔 없는지)
- [ ] **시장/지역/버전이 둘인가** — 국내 vs 해외, 만화식 vs 웹툰, 논문 라인 vs 리포트 라인
- [ ] **정상 경로 외에 폴백·기본값·재시도 경로가 있는가** (모델 전환이 폴백엔 안 번지는 사례가 잦다)
- [ ] **UI라면 같은 패턴이 몇 화면에 있는가** — 툴팁·빈 상태·헤더·배지는 반드시 grep으로 센다
- [ ] **실행 환경이 둘 이상인가** (v1.1) — 같은 코드라도 도는 환경마다 설정·권한이 다르다.
      로그인 안 한 사용자 vs 로그인한 사용자(역할별 timeout 이 달라 한쪽만 죽음, k-vivino
      `3362c33` 09-18), 정식 채널 vs 베타·테스트 채널(production 만 막고 login-test 는 빠뜨림,
      `be96af4` 09-27), 처음 설치한 앱 vs OTA 로 받은 번들(베타 APK 에 공용 테스트 계정이 실림,
      `832cbde` 10-04), 로컬 실행 vs CI·서버 실행.

### 1-b. 값·상태를 바꿀 때는 "쓰는 곳"부터 센다 (v1.1)
가드를 더하는 경우가 아니라 **값 자체를 들이거나 바꾸는** 경우에도 같은 결함이 난다. 바꾸는 순간
그 값을 읽는 곳이 전부 영향을 받는데, 한 곳씩 사고가 나서야 차례로 고친 사례가 반복됐다
(Aria 09-28 시즌 2 전환 사고 사슬, 10-01 교정 컬럼이 PR 3개에 걸쳐 순차 전파).
- [ ] 바꾸기 **전에** 그 값·컬럼·상태를 읽는 소비처를 grep 으로 **전부** 목록으로 만들었는가?
- [ ] 목록 전부를 **한 PR 에서** 처리하고, 새 소비처가 생겨도 빠지지 않게 테스트로 고정했는가?
      모범안: Aria `36f2da3`(#633, 10-04) — 목표가 이상치 표시 칸을 추가하면서 그 값을 쓰는
      소비처 7곳을 한 PR 에서 모두 제외 처리하고 테스트로 묶었다.
- [ ] 함수를 고쳤다면, **실제 진입점이 새 인자·새 입력을 넘기는지**도 봤는가? 함수는 고쳤는데
      호출하는 쪽이 옛 인자로 불러 효과가 없던 사례(VIDEO-ARTICLE `285f576` 09-24 원문 확보 수준이
      게이트에 닿지 않음, `4b33adb` 09-25 정규화에 Fact Sheet 일부만 넘김).

### 2. 추정하지 말고 실측한다
- [ ] 목록을 머리로 세지 말고 `grep`/`rg`로 실제 호출부·유사 패턴을 뽑았는가?
- [ ] SQL 함수·트리거처럼 코드 밖에 있는 소비자도 훑었는가? (`pg_index`·`pg_get_functiondef` 등)
- [ ] 각 경로에 대해 "여기는 왜 안 고쳐도 되는가"를 한 줄로 답할 수 있는가? 답이 안 되면 고친다.
- [ ] 저장된 데이터로 **함수만** 불러 본 검증은 배선 결손을 못 잡는다(`285f576`). 실제 진입점을
      한 번 통과시켜 봤는가? (`render-required-verification-audit`)

### 3. 사고 전에 선제 적용한다
- [ ] 지금 고치는 결함과 **같은 계열**이 아직 안 터진 경로에 잠재해 있지 않은가?
      (Aria `b2f0142`가 이 처방의 참조 구현이다 — 08-19에 실제로 터진 UUID 바인딩 결함이 아직
      배선되지 않은 Shadow 서비스 7종·12개 지점에 잠재한 것을 목록화해 "배선하는 순간 재현된다"며
      미리 제거하고 전수 정적 계약 테스트로 고정했다.)
- [ ] 반복을 없앨 수 있으면 경로별로 고치지 말고 **공용 헬퍼/단일 함수로 모은다** —
      경로가 늘어날 때마다 같은 실수가 반복되는 구조 자체를 없애는 편이 낫다.

## 사용 방법
가드·연결·설정·프롬프트 규칙을 바꾸는 커밋 직전에 §1 목록을 만들고 §2로 실측한다.
목록에서 하나라도 "확인 안 했다"가 남으면 커밋하지 않는다. 경로가 셋 이상이면 개별 수정보다
공용화(§3)를 먼저 검토한다. 값을 들이거나 바꾸는 커밋이면 §1-b 를 먼저 한다.
