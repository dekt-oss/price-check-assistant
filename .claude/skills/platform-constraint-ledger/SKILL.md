# Platform Constraint Ledger

## 언제 쓰나
- 새 수집 스크립트·조회 코드·배치를 작성할 때 (특히 이미 있는 것과 비슷한 일을 하는 새 스크립트)
- 마이그레이션·DB 함수·인덱스를 새로 쓸 때
- 배포 설정(워크플로 권한, 빌드 명령, 시크릿)을 건드릴 때
- 외부 API를 새로 붙이거나 플랜·키를 바꿀 때

## 왜 필요한가
**2개 레포 11회.** 그런데 성격이 도중에 바뀌었다 — 초반엔 "문서에 없는 제약을 처음 만난다"였는데,
후반부터는 **이미 이 저장소가 겪고 고친 제약을 새 코드가 다시 밟는다.** 그래서 처방이
"조심하기"가 아니라 "만난 제약을 적어 두고 대조하기"가 됐다.

같은 제약이 두 번 이상 재발한 것:
- **PostgREST 기본 1,000행 캡** — k-vivino `619d53a`(MFDS 스캔 1,497행 중 28% 잘림, "중복 없음"처럼
  보임) → `8d5a1c9`(`loadSites()`가 `.range()` 없이 읽어 1,351곳 중 351곳 누락, `order`도 없어
  **어느 351곳이 빠지는지 실행마다 달랐다**) → VIDEO-ARTICLE `dd21fc2`(같은 캡 + `.in()` 목록
  길이 한계로 fetch 자체가 죽음)
- **운영 안정성 패턴 미재사용** — k-vivino `2c12bee`가 타임아웃·PID·하트비트 없이 새 수집기를 짜
  소켓 154분 행·유령 프로세스·60분 무신호 정지를 겪었다. 커밋이 스스로 *"이 저장소가 이미 겪고
  고친 문제였다(`fb61170`)"* 고 밝혔다.

한 번씩 만난 것:
- **VIDEO-ARTICLE** `70dc516` — PostgREST `on_conflict`이 `coalesce()` 표현식 인덱스를 못 타깃(42P10)
- **VIDEO-ARTICLE** `f1dfa0d` — OpenAlex `from_created_date`가 유료 플랜 전용
- **VIDEO-ARTICLE** `27124f4` — GitHub Actions `permissions` 블록을 하나라도 선언하면 명시 안 한 권한은 전부 none
- **VIDEO-ARTICLE** `3baee92` — Supabase Storage 실제 과금은 `storage.objects` 테이블이 아니라 S3
  실사용량 기준. **존재하고 그럴듯한 함수**(`get_size_by_bucket()`)가 실제 판정 기준이 아니었다
- **k-vivino** `83932aa` — Vercel `buildCommand` 256자 제한
- **k-vivino** `d6053a9` — `pg_trgm` 파라미터는 확장이 로드되기 전엔 미등록이라 같은 파일에서 먼저 로드해야 하고, 세션 스코프라 파일을 쪼갤 수 없음
- **k-vivino** `7fcbdd5` — 판매처가 핫링크(리퍼러) 차단(401). API 계약이 아니라 **판매자 측 접근 제어**
- **k-vivino** `30d221c` — API 역할의 "WHERE 없는 DELETE 금지" 가드가 **SECURITY DEFINER 함수 내부**에도 적용됨
- **k-vivino** `6aaf51f`(2026-09-04) — `plpgsql_check`가 함수 안의 런타임 `create temporary table`을
  해석 못 해 함수를 통째로 막음. 함수당 첫 오류에서 멈춰 같은 패턴 두 번째는 뒤에 숨어 있었다

## 절차

### 1. 원장을 둔다 (최초 1회, 레포별)
- [ ] `docs/platform-constraints.md`(또는 해당 레포 관례에 맞는 위치)에 **이 저장소가 실제로 만난
      제약**을 적는다. 항목마다: 플랫폼 · 제약 내용 · 어떤 증상으로 나타났나 · 처방 · 커밋 해시
- [ ] 증상을 반드시 적는다. 다음 사람이 만나는 것은 제약 이름이 아니라 **증상**이다
      ("에러 없이 결과가 적다", "성공했는데 반영이 안 됐다").

### 2. 신규 코드 작성 전 대조
- [ ] 지금 쓰려는 것과 **같은 플랫폼·같은 종류의 작업**이 원장에 있는가?
- [ ] 조회 코드라면: 행 상한(`range`/페이징)·`order` 고정·목록 길이 한계를 처리했는가?
- [ ] 수집 스크립트라면: 타임아웃·프로세스 종료·진행 하트비트를 **기존 스크립트에서 가져왔는가?**
      (새로 짜지 말고 검증된 것을 재사용한다 — `2c12bee`의 교훈)
- [ ] 마이그레이션·DB 함수라면: 확장 로드 순서, 정적 검사기(plpgsql_check) 해석 한계, 역할 가드를 고려했는가?

### 3. 새 제약을 만났을 때 (실행 실패로 알게 된 경우)
- [ ] **그 자리에서 원장에 추가한다.** 고치고 넘어가면 다음 스크립트가 같은 것을 밟는다.
- [ ] "존재하고 그럴듯한 함수/필드가 실제 판정 기준인가?"를 확인했는가?
      (Supabase Storage 사례 — 있는 함수를 읽고 "집계 기준이 맞다"고 오판했다)
- [ ] 정적 검사기가 막은 경우, **함수당 첫 오류에서 멈추므로** 같은 패턴이 뒤에 더 있는지 함께 훑었는가?

## 사용 방법
새 수집기·조회·마이그레이션을 쓰기 **전에** §2로 원장을 대조한다. 실행 실패로 새 제약을 만나면
고치는 김에 §3으로 원장에 남긴다. 원장이 없는 레포라면 §1을 먼저 만든다 — 이 스킬의 가치는
체크리스트가 아니라 **레포별로 쌓이는 원장 자체**에 있다.
