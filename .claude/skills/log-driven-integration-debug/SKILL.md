# Log-Driven Integration Debug

## 언제 쓰나
- 외부 API(LLM 공급자, 지도/geocode, 결제 등) 연동이 프로덕션에서 실패하는데, 실패 모드가
  하나가 아니라 여러 겹으로 의심될 때
- "아마 이것 때문일 것"이라는 가정이 있지만 실제 로그로 확인하지 않은 상태에서 고치려 할 때
- CI 워크플로가 특정 단계에서만 반복적으로 실패하고, 실패 사유가 로그만 봐서는 바로 안 보일 때

## 왜 필요한가
외부 연동 장애는 원인이 한 겹이 아니라 여러 겹으로 쌓여 있는 경우가 많다. 원인을 추측해서
한 번에 여러 곳을 고치면, 어느 수정이 실제로 효과가 있었는지 알 수 없고 새 겹이 드러날 때마다
다시 헤매게 된다. 관찰된 사례:
- VIDEO-ARTICLE: Veo(Google Files API) I2V 연동에서 4연속 커밋이 각각 실제 렌더 로그로 원인을
  확인하며 순차 수정 — ①프리뷰 모델 미지원 파라미터(400) → ②완료 응답 파싱 방식 → ③파일
  다운로드 `alt=media` 누락(400) → ④리다이렉트 미추적으로 깨진 mp4 저장 (`741a2d6`→`ef8a54b`,
  2026-07-12)
- k-vivino: geocode CI가 4연속 커밋으로 순차 수정 — ①secret 이름 불일치 → ②Node 버전 WebSocket
  미지원 → ③인증 실패 조기중단·진단 로그 추가 → ④실제 원인은 키가 아니라 인증 헤더 방식
  불일치 (`eefe92d`→`9d06243`, 2026-07-13)
- Aria: 리포트 중요도 v2의 Gemini 정형 출력 실패를 4단계로 진단 — ①채점 상태·실패 원인을
  UI에 먼저 노출 → ②JSON 계약·파싱 진단 보강 → ③원인 확정(Gemini 2.5 thinking이 completion
  토큰을 먼저 소비해 JSON이 비거나 잘림) → `reasoning_effort=none` 강제 → ④그래도 빠듯한
  출력 상한을 실측 기준으로 상향 (`0b7966a`→`d72e39e`, 2026-07-17)

패턴: **매 커밋이 "추측 수정"이 아니라 "로그로 확인된 원인 하나"를 고쳤다.** 그 결과 되돌리기
없이 순방향으로만 수렴했다. 이건 사고가 아니라 "추측 수정 금지" 원칙이 실전에서 잘 지켜진
긍정적 사례이기도 하다 — 이 스킬은 그 절차를 재사용 가능한 형태로 굳힌다.

## 절차
1. **원인을 먼저 가정하지 않는다.** 실패가 재현되는 실제 로그(API 응답 본문, HTTP 상태 코드,
   렌더/CI 로그)를 먼저 확보한다. 로그가 없으면 로그부터 추가한다(위 사례들의 1단계가 전부
   "상태/실패 원인을 보이게 만드는" 커밋이었다).
2. **한 커밋 = 한 가설.** 로그에서 확인된 가장 앞단의 실패 원인 하나만 고친다. 여러 겹이
   의심돼도 한 번에 다 고치지 않는다 — 다음 겹은 이번 수정 후 다시 로그를 봐야 보인다.
3. **수정마다 재검증.** 고친 뒤 실제로 재현시켜(재실행/재배포/재호출) 이번 겹이 해소됐는지
   확인한다. 해소됐지만 여전히 실패하면 다음 겹으로 넘어간다 — 이게 정상이다, 재발이 아니다.
4. **원인이 확정되면 회귀 테스트로 고정한다.** 각 사례 모두 원인 확정 커밋에 유닛테스트가
   같이 들어갔다(예: Aria `test_gemini_structured_calls_disable_thinking_and_require_json`).
5. **다 해소되면 체크리스트로 남긴다.** 같은 외부 서비스에 대한 다음 연동(다른 프로젝트
   포함)에서 반복하지 않도록, 이번에 밝혀진 실패 모드를 프로젝트 문서에 정리한다
   (예: VIDEO-ARTICLE `docs/google-files-api-checklist.md`).

## 사용 방법
외부 연동 장애를 진단할 때, "고칠 것 같은 걸 다 고치고 재배포"하지 말고 위 5단계를 따른다.
특히 1번(로그 먼저)과 2번(한 커밋 한 가설)이 핵심 — 이 둘만 지켜도 대부분의 "고쳤는데 왜
아직도 안 되지" 왕복을 줄인다.
