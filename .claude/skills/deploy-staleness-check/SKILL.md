# Deploy Staleness Check

## 언제 쓰나
- Edge Function(Supabase 등) 코드를 수정한 PR을 머지·배포할 때
- 새 DB 마이그레이션이 딸린 PR을 배포할 때
- 배치/스케줄 잡이 만든 캐시된 payload를 읽는 화면을 바꿀 때
- "코드는 고쳤는데 프로덕션에서 여전히 옛날처럼 동작한다"는 버그를 진단할 때

## 왜 필요한가
머지·배포 자동화가 있어도 "실제로 반영됐는지"는 별개로 확인해야 한다. 관찰된 사례:
- VIDEO-ARTICLE: Edge Function 자동배포 워크플로를 도입했지만 `SUPABASE_ACCESS_TOKEN`이 실제로는
  등록 안 돼 있어 배포가 안 걸림 (`9bc6893`→`87de308`→`bf9e714`)
- VIDEO-ARTICLE: 새 마이그레이션(0016/0017)이 라이브 DB에 미적용 상태로 남아, 기능 활성화 직후
  렌더 파이프라인 전체가 막힘 (`c8ae6ee`)
- k-vivino: 배포돼 있던 Edge Function이 옛 스텁이라 스캔 AI 기능이 죽어 있었음 (`7aa3d8d`)
- ARIA: 신규 필드가 배포됐지만 주1회 배치가 저장한 캐시 payload를 화면이 읽는 구조라, 배치
  재실행 전까지 반영 안 됨 (`eac8c2f`)

패턴: **"배포/머지 완료" ≠ "실제 반영 완료".** 재배포·재적용·재실행이라는 별도 계기가 빠지면
조용히 옛 버전이 계속 돈다.

## 체크리스트

### Edge Function / 서버리스 함수를 고친 경우
- [ ] CI가 실제로 배포 스텝을 실행했는가? (워크플로 로그에서 스킵 없이 성공했는지 확인)
- [ ] 배포에 필요한 시크릿(access token 등)이 실제로 레포/프로젝트에 등록돼 있는가?
      (플레이스홀더·만료 여부 확인)
- [ ] 배포 후 함수를 실제로 한 번 호출해 응답이 새 코드를 반영하는지 확인했는가?

### DB 마이그레이션이 딸린 경우
- [ ] 마이그레이션 파일이 레포에 있다는 것과 라이브 DB에 실제로 적용됐다는 것은 다르다 —
      `supabase migration list`(또는 동일 도구)로 라이브 상태를 직접 확인했는가?
- [ ] 마이그레이션에 의존하는 코드가 먼저 배포되면 어떤 실패 모드가 나는가? 조용한 스킵인가,
      명시적 에러인가? CI 워크플로에 `continue-on-error`가 없으면 한 스텝 실패가 뒤 스텝
      전체를 막을 수 있다.

### 배치/캐시에 의존하는 화면·필드를 바꾼 경우
- [ ] 이 화면은 실시간 쿼리인가, 배치가 저장한 캐시 payload를 읽는가?
- [ ] 캐시라면, 다음 정기 배치까지 기다리지 않고 수동으로 재실행할 트리거가 있는가? 없다면
      하나 만드는 것을 고려한다.
- [ ] 배포 직후 실제 화면에서 새 필드/값이 (재실행 없이) 보이는지 눈으로 확인했는가?

## 사용 방법
PR을 머지·배포하기 직전, 또는 "배포했는데 반영이 안 된다"는 증상을 진단할 때 위 체크리스트를
훑는다. 프로젝트마다 실제 배포 표면(Edge Function/마이그레이션/배치)이 다르므로 해당 없는
항목은 건너뛴다.
